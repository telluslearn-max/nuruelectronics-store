## Design-twice items

### `src/lib/shopify/index.ts` — Special-General Mixture (Critical)

The mock/real branch repeats in all 11 exported functions, and the mock-only query-matching
engine is embedded in the same file as the real GraphQL client.

**Option A — Adapter interface: one `CatalogClient` shape, two implementations, chosen once.**
Define an interface matching the current public API; implement it twice (`shopify-client.ts` for
real-fetch bodies, `mock-client.ts` for mock bodies including the query-matching engine).
`index.ts` picks one instance at module load and re-exports its methods as today's free functions.
- Pros: real and mock implementations become independently readable; the query-DSL matcher moves
  to live beside the only data it's relevant to.
- Cons: biggest-diff option — every function body moves, touching ~500 lines for no external
  behavior change; introduces an interface type that must stay in sync with the free functions it
  wraps.

**Option B — Push the mock branch to the top; extract only the mock bodies.**
Move every mock-mode function body (query-matching engine included) into `shopify/mock-adapter.ts`
exporting `mockGetProducts`, etc. Each function in `index.ts` becomes a one-line dispatch followed
by the unchanged real-fetch body.
- Pros: much smaller, lower-risk diff — no call-site changes; immediately makes the mock engine
  readable as one coherent unit instead of scattered across 11 functions.
- Cons: doesn't fully solve the mixture — each function still opens with a mock dispatch line, so
  a reader still learns "this file also has a mock mode" 11 times, just with one line of noise
  instead of several.

**Recommendation**: Option B first — safer, smaller, and removes the worst offender (the embedded
query DSL) immediately. Revisit Option A only if the mock path keeps growing.

### `src/lib/pdf/receipt-document.tsx` + `invoice-document.tsx` — Repetition / Special-General Mixture (Critical)

`document-layout.tsx` already has a proven, general `LineItemsTable`/`TotalsBlock` pair that
`estimate-document.tsx` uses successfully; receipt and invoice maintain their own parallel,
drifting copies.

**Option A — Migrate receipt and invoice fully onto `DocumentShell` + shared components, adding a
header customization point to `DocumentShell`.**
- Pros: one source of truth for every document's table/totals layout — the column-ratio drift
  disappears permanently; both files shrink close to `estimate-document.tsx`'s size.
- Cons: `DocumentShell`'s interface grows a customization axis it doesn't have today, pulling
  against its current shallow, easy-to-use shape; receipt's payment-method block and invoice's
  amount-due box still need their own slot regardless, so props surface grows non-trivially for
  two genuinely different documents.

**Option B — Share only the line-items table and totals block; leave headers bespoke.**
Swap the hand-rolled item-row/totals JSX and styles for the existing `LineItemsTable`/
`TotalsBlock` imports, leaving header/footer layout untouched.
- Pros: small, low-risk change confined to the part that's genuinely identical in shape across all
  three document types; fixes the observed column-ratio inconsistency immediately.
- Cons: doesn't fully unify the files — two separate style systems remain in play, just with less
  overlap.

**Recommendation**: Option B first — directly fixes the drift bug with a small, low-risk diff, and
doesn't force a premature abstraction onto headers that have real content differences. Revisit
Option A only if the headers themselves start converging.

### `src/lib/pdf/document-layout.tsx` — Information Leakage on the `styles` export (Critical)

**Option A — Stop exporting raw styles; add typed layout primitives** (`<SectionLabel>`,
`<TwoColumnBlock>`, a configurable `<Table columns={...}>`) that wrap the styling internally,
matching the pattern `DocumentShell`/`LineItemsTable`/`TotalsBlock` already use.
- Pros: consumers compose real components instead of raw style objects; an internal restyle no
  longer breaks 3 unrelated files; brings the module up to the "deep module" standard its own best
  parts already meet.
- Cons: touches all 3 consumer files, and their bespoke arrangements need equivalent new
  primitives — new design surface, risks under/over-generalizing on the first pass.

**Option B — Split the exported `styles` into a documented public subset and an unexported
`DocumentShell`-internal subset.** Move keys nothing outside the file uses into `internalStyles`,
keep only genuinely shared keys in the exported `styles`, with a comment marking it a contract.
- Pros: near-zero churn to the 3 consumer files; still shrinks the leak surface.
- Cons: doesn't remove coupling on the keys that stay public — narrows and documents the leak
  rather than closing it.

**Recommendation**: Option A is the real fix but sizable; land Option B first as the immediate,
low-risk narrowing, and treat Option A as the follow-up once a 4th or 5th bespoke document shows
up and the duplicated markup gets worse.

### `src/lib/pdf/document-layout.tsx` — Information Leakage on `WARRANTY_TERMS` (Critical)

**Option A — Single structured source, two renderings.** Extract the policy into a shared data
file (e.g. `src/lib/warranty-policy.ts`) carrying both a full-prose form (legal page) and a
condensed `{label, summary}` form (PDF), imported by both.
- Pros: a policy change updates one file and both renderings follow; removes the risk the current
  comment apologizes for rather than solves.
- Cons: the two renderers genuinely want different content shapes — forcing a single shape risks
  its own over-general abstraction unless the condensed form is modeled as a deliberate derived
  view of the full one.

**Option B — Leave the two copies, add an enforced sync tripwire** (a check that fails CI if one
side's content changes without a corresponding change to the other, e.g. a content-hash
comparison with an explicit acknowledge-the-diff step).
- Pros: cheap; doesn't force two rendering contexts into one data model; keeps the deliberately
  condensed PDF copy exactly as condensed as it is today.
- Cons: doesn't remove the duplication, only flags drift; brittle against wording-only edits, and
  a meaning-changing edit that dodges the hashed sentences could false-negative.

**Recommendation**: given this content governs actual customer refund/warranty claims (real-dollar
adjacent, the same reasoning that puts `ledger.ts` on the financial-risk floor), Option A is worth
the modeling effort.

### `src/lib/email.ts` — Special-General Mixture (Critical)

Same shape as the 2026-08-24 `admin-actions.ts` finding: a generically-named file that actually
contains 3 unrelated business domains' worth of content.

**Option A — Split by domain**, mirroring the per-feature layout already used in
`capital-circle/`, `shopify/`, `concierge/`: `email-transport.ts`, a Capital Circle notifications
file, a product-readiness notifications file, and `document-email.ts` for the 6 document-lifecycle
functions.
- Pros: each file becomes independently understandable; consistent with the repo's own
  established per-domain layout.
- Cons: all 9 domain-specific functions funnel through the 2 shared transport functions —
  splitting into 4 files means those either move to a 5th shared file (extra import hop
  everywhere) or get duplicated per domain file, reintroducing the Repetition problem flagged
  above.

**Option B — Extract only the genuinely general transport primitives, keep the rest together**
(same shape as the recommended fix for `admin-actions.ts`): pull `sendDocumentEmail`,
`sendPlainEmail`, `escapeHtml`, `isEmailConfigured` into `email-transport.ts`; leave the 3
business-domain groups in `email.ts`, banner-commented by domain.
- Pros: low-risk, low-churn — matches the fix pattern already recommended once this loop; removes
  the worst of the mixture without fragmenting three still-small domain groups into sub-40-line
  files.
- Cons: still leaves 3 unrelated business domains sharing one file long-term; the file's name
  stays inaccurate unless it's also renamed.

**Recommendation**: Option B now — the transport extraction is a clean, self-contained, ~40-line
piece with an obvious boundary. Revisit Option A only if a 4th unrelated notification domain gets
added.

### `src/lib/support-actions.ts` — Repetition (Critical)

**Option A — extract a shared `transitionReturnCase` helper** parameterized by the validation
predicate, the update payload, and optional journal lines.
- Pros: collapses ~100 lines of near-identical scaffolding into one place; a new case-transition
  becomes a ~10-line call instead of copy-pasting a whole function; the validate → transact → log
  → redirect sequence can only drift in one place.
- Cons: the three current transitions aren't quite uniform (`markCaseRefunded` validates an extra
  field; `approveEscalatedCase` validates an amount before entering the transaction) — the
  helper's parameter surface has to grow, and a sufficiently general helper risks becoming its own
  Shallow-Module problem.

**Option B — factor out only the strictly-identical tail** (transaction wrapper + `logAdminAction`
+ `revalidatePath` + `redirectWithSuccess`), leaving case-specific validation and update payload
inline in each function.
- Pros: much smaller, safer change — each function keeps its own validation logic fully readable
  in place; only the part that's genuinely identical across all three is removed.
- Cons: leaves the "fetch case, validate expected prior status, redirect if wrong" block — the
  largest single chunk of duplication — untouched in all three functions.

**Recommendation**: Option B first (low-risk, addresses the tail only), then revisit Option A once
a fourth transition type appears (there's already a natural fourth: reopening a denied case).

### `src/lib/support/return-policy.ts` — Information Leakage (Critical)

The 7-day / 48-hour / 365-day windows exist as both a decision input and independently-authored
customer-facing prose in two other pages.

**Option A — single source of truth: export the windows in human-readable form and interpolate
them into the two page components** instead of hand-typed prose.
- Pros: genuinely eliminates drift risk — changing the constant changes both pages automatically;
  small, surgical diff on the two page files.
- Cons: legal/marketing copy dictated by a numeric constant is an awkward coupling in the other
  direction; the surrounding sentence structure is still duplicated as a string template across
  two pages even once the number is shared. The warranty page says "1-year warranty" rather than
  "365-day," needing a small derived formatter.

**Option B — add a lightweight CI check** (in the style of `check-commit-comment-ratio.mjs`) that
greps the legal/returns pages and `return-policy.ts` for the numbers and fails on disagreement.
- Pros: no runtime coupling between policy logic and marketing copy, which needs to stay free-form
  English; catches drift at PR time instead of trusting a comment.
- Cons: a regex-based check is brittle against rewording; another script to maintain for a
  low-frequency drift risk; doesn't reduce the duplication, just polices it.

**Recommendation**: Option A for the two business-tunable windows (7-day, 48-hour); accept the
residual sentence-template duplication rather than over-engineering a copy-generation system for
three sentences of legal text.

### `src/lib/spec-glossary.ts` / `src/lib/shopify/queries.ts` — Information Leakage (Critical)

The set of valid spec keys is declared three times by hand across a GraphQL block, a label/
category map, and a glossary map.

**Option A — a single `SPEC_REGISTRY` that all three consumers derive from**, generating the
GraphQL `identifiers` block, the label map, and the glossary map from one array of
`{key, label, category, glossary}` objects.
- Pros: genuinely closes the leak — adding a spec key becomes a single array entry, impossible to
  add to only one of the three consumers; the "must reproduce key order" constraint on
  `SPEC_CATEGORIES` disappears because order is defined once.
- Cons: the "coming-soon" `release_date` key deliberately lives in a different GraphQL namespace
  than the rest (`availability`, not `specs`) to avoid a metafield collision — a flat registry
  needs a `namespace` field per entry to preserve that distinction. Bigger diff — three files
  change instead of the comments-only status quo.

**Option B — leave the three lists as-is, add a build-time or test-time consistency check**
asserting the three key sets agree (modulo intentionally-ungloss aried keys).
- Pros: much smaller change, no risk to the deliberate namespace split; turns "silently drifts"
  into "CI fails with a clear diff."
- Cons: doesn't reduce the duplication itself, just detects it after the fact — three files still
  need three manual edits per new spec key.

**Recommendation**: Option B first as a fast, low-risk win, with Option A as a follow-up if the
spec-key list keeps growing — at 24 keys across three files it's already past the point where a
registry pays for itself, but the namespace wrinkle deserves a deliberate pass rather than a
mechanical merge.
