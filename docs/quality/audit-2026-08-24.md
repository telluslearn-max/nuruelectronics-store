## Design-twice items

### `src/lib/admin-actions.ts` — Special-General Mixture (Critical)

The file mixes four document types' full CRUD + email lifecycles in one module, at rank #26 of
419 by complexity score (churn 17 touches in 6 months, financial-risk floor applied as a
money-touching `*-actions.ts` file). Two alternative designs, per Ch. 11 ("Design It Twice"):

**Option A — split by document type into `estimate-actions.ts`, `invoice-actions.ts`,
`delivery-note-actions.ts`, `document-bulk-actions.ts`.**
- Pros: each file becomes independently understandable; matches the per-feature layout already
  used successfully in `capital-circle/`, `shopify/`, `concierge/`; a developer working on invoice
  logic never has to scroll past estimate code.
- Cons: `createInvoiceFromEstimate` (line 274) and the bulk-operation functions (lines 966, 983)
  genuinely span multiple document types — they'd need to live somewhere, or import across the
  four new files, which reintroduces a coupling the split was trying to remove. Four smaller
  files also means four import statements everywhere one document type's actions are used
  alongside another's (e.g. the order detail page, which touches estimates AND invoices AND
  delivery notes on one screen).

**Option B — keep one file, but restructure internally by grouping with clear section comments
and extracting only the genuinely shared plumbing (e.g. a shared "post document email" helper
already used by four of the `send*Email` functions) into a `document-email.ts` sibling.**
- Pros: no call-site churn (nothing importing from `admin-actions.ts` today has to change); the
  document-lifecycle functions that legitimately need to see each other (`createInvoiceFromEstimate`
  reading both estimate and invoice logic) stay adjacent; smaller, lower-risk change.
- Cons: doesn't reduce the file's line count or its "everything lives here" cognitive load for a
  new contributor; the module still doesn't have a name that describes what it does (Ch. 14: "hard
  to pick a name" is itself a red flag, and `admin-actions.ts` is about as generic a name as this
  file could have).

**Recommendation for whoever picks this up**: lean toward Option A for the three document types
that don't cross-reference each other (delivery notes, and the estimate/invoice pair minus
`createInvoiceFromEstimate`), and keep `createInvoiceFromEstimate` plus the bulk-operation
functions in a small `document-shared-actions.ts` that the split-out files both depend on — a
hybrid that gets most of Option A's clarity without Option B's "everything stays coupled" cost.
This is exactly the kind of finding this audit is supposed to hand off, not resolve unilaterally
in a seed run — filed as a GitHub issue (see below) rather than executed here.
